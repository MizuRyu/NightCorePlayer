# ADR 003: 残高管理は秒演算の `nextResetAt` と曲境界停止で設計する

> Status: Accepted
> Date: 2026-08-23

## Context

Nightcore 変換（`playbackRate != 1.0`）にフリーミアム課金を導入するにあたり、次を決める必要があった。

- 無料枠の日次リセットをどう実装するか
- 端末の時計が不正に操作された場合にどう扱うか
- トライアル期間の判定方法
- 残高が尽きた瞬間にどう振る舞うか

今回の調査・実装で次が分かった。

- 日付文字列（例: `"2026-08-23"`）でリセットを判定すると、タイムゾーンが変わる（海外渡航、iOS 側の自動タイムゾーン変更）だけで日付が変わり、意図しない二重リセットが起きる
- `Calendar` ベースの「日が変わったか」判定は、上記に加えて夏時間・カレンダー設定にも依存し、テストしにくい
- 端末の時計を意図的に戻せば、日次リセットやトライアルを繰り返し得られてしまう
- 残高が尽きた瞬間に再生を止めると、BGM として流している最中に曲の途中でブツ切りになり体験を大きく損なう

## Decision

### 1. 日次リセットは `nextResetAt: Date` の秒演算で行う

`AllowanceSnapshot.nextResetAt` に「次にリセットすべき時刻」を `Date` として持ち、`guardedNow >= nextResetAt` になったら `remainingSeconds` を `dailyFreeSeconds` に戻し、`nextResetAt` を `guardedNow + 86400秒` に進める（`AllowanceServiceImpl.normalizedSnapshot`）。

日付文字列や `Calendar` の「日が変わったか」判定は使わない。`Date` の単調な前進だけで判定できるため、タイムゾーン変更やカレンダー設定に左右されない。

### 2. 時計逆行ガード（`guardedNow`）

`guardedNow = max(now, lastSeenAt)` を全ての時刻参照の起点にする（`AllowanceServiceImpl.guardedNow`）。端末の時計を過去に戻しても、アプリが内部的に扱う「現在時刻」は `lastSeenAt` を下回らない。これにより、時計操作によるリセットの繰り返し取得・トライアルの延長を防ぐ。

トライアル判定（`isTrialActive`）だけは例外で、`now` が `firstLaunchAt` より 1 時間以上過去なら無効化する `trialClockToleranceSeconds` を設けている。厳密に `guardedNow` だけで判定すると、初回起動直後に時計を数分戻しただけの正常なケース（NTP 同期のずれ等）までトライアルを無効化してしまうため、1 時間の許容幅を持たせている。

### 3. トライアルは初回起動から 168 時間（7日）固定

`firstLaunchAt` を基準に `trialDays（7）* 86400秒` を加算した時刻をトライアル終了時刻とする。日数ではなく秒で計算するため、リセット判定と同じ理由でタイムゾーンに影響されない。

### 4. 残高枯渇時は即停止せず、曲境界で止める

`AllowanceEnforcer` は「残高0 かつ 倍速再生中」を検知した時点では再生を止めず、猶予を与えた曲のID（`graceSongID`）を記録して `.exhaustedPendingSongEnd` イベントを発行するだけにする。実際の停止は、曲が自然に終わるタイミングで `MusicPlayerServiceImpl` 側が `shouldStopAtSongBoundary()` を確認して行う。

BGM として流している利用シーンを想定すると、曲の途中で無音になるより、その曲を最後まで聴かせてから止める方が体験を損なわない。

猶予は「**倍速で再生している最中に残高が尽きた**」場合だけに与える。残高が尽きた状態から倍速へ変更した場合は猶予を与えず、曲末を待たず等速へ戻す（`shouldRevertToNormalRateNow()`）。等速は無料のため再生自体は止めない。

当初は「残高0で倍速再生を検知したら1曲ぶん猶予」としていたが、これは残高0の状態から倍速へ入れる操作にも猶予を与えるため、曲を選び直すだけで1曲まるごと無料で倍速再生できた。実機検証で「残り0分なのに倍速で鳴る」という指摘が繰り返し出たのはこの挙動による。

本設計が避けたいのは**鳴っている音楽が途中で切れること**であり、まだ鳴っていない曲を倍速で始める操作まで許す理由はない。猶予の条件を「再生中に尽きた場合」に限定することで、ADR の意図を保ったまま実害を「残高が尽きた曲の残り時間」に閉じ込める。

猶予は曲ID（`graceSongID`）と「猶予を使ったか」（`hasUsedGrace`）で持つ。フラグだけだと等速へ戻した時点で解除され、倍速へ戻すことで曲ごとに取り直せてしまうためである。

速度を戻すときは `.revertedToNormalRate` を発行し、理由を伝えるダイアログを出す。無言で等速へ戻すと、ユーザーには不具合に見える。

### 5. リワード視聴は1日の回数上限を持つ

リワードの視聴回数はアプリ側で1日 `dailyRewardLimit`（5回）までに制限し、日次リセットで戻す。
AdMob 側に固定の上限は存在せず、管理画面のフリークエンシーキャップも任意設定のため、
上限を持たないと理論上は無限に時間を追加できてしまう。無料枠1時間 + 30分×5回 = 最大3.5時間/日。
UI 側でボタンを塞ぎ、サービス側 (`grantReward`) でも重複付与を止める二段構えにする。

## Scope

対象:

- `AllowanceService` / `AllowanceEnforcer` の残高管理・消費・停止タイミング

対象外:

- Pro 購入フロー自体（StoreKit 2 のトランザクション検証は `ProStoreService` の責務）
- Apple Music の等速再生（残高ゲートの対象外。[ADR 002](./002-no-pitch-independent-control.md) 参照）

## Consequences

### Pros

- タイムゾーン変更・夏時間・カレンダー設定変更のいずれでも二重リセット/リセット漏れが起きない
- 時計を戻す単純な不正では残高を増やせない
- 曲境界停止により、枯渇時の体験がブツ切りにならない

### Cons

- `guardedNow` により、正当な理由（デバイス間同期のずれ等）で時計が多少前後した場合も一律で「戻さない」扱いになる。トライアル判定にだけ 1 時間の許容幅を設けているが、他の判定には無い
- 枯渇後も曲の残り時間ぶんは倍速再生が続く。その間の消費時間は `consume()` でさらに `remainingSeconds` がマイナス方向には行かない（`max(0, ...)` でクランプ）ため、実害は「止まるまでのタイムラグ」のみ
- 再生位置が継続的に取れない場合は wall-clock フォールバックになる。再生中とみなされている間はスタール中でも経過実時間ぶんを消費し得るが、上限は経過実時間であり、旧仕様の 60 秒クランプにあった過少消費よりは実態に近い

## Rejected Alternative

### 1. 日付文字列 + `Calendar.isDateInToday` での判定

却下理由:

- タイムゾーン変更・夏時間で二重リセットが起きる
- テストが `Calendar` のロケール・タイムゾーン設定に依存し不安定になる

### 2. 残高0を検知した瞬間に即座に再生を止める

却下理由:

- 曲の途中で無音になり、特に BGM 用途での体験が著しく悪化する

### 3. 時計逆行を検知したらエラーにする / トライアルを即無効化する

却下理由:

- 正当な時刻同期のずれまで弾いてしまい、実装・検証コストの割に得られる不正対策効果が小さい。`guardedNow` で「進めない」だけにする方がシンプルで十分

## Implementation Notes

- `consume()` は等速再生時・トライアル中は呼ばれない（`AllowanceEnforcer.tick` 側でガード）
- 1 tick あたりの消費時間は「実際に進んだ再生位置」から求める。前回 tick と同じ曲で両方の再生位置が取れた場合は `min(wallDelta, max(0, positionDelta) / max(rate, 1.0))`、曲が変わった tick や再生位置が取れない tick は `wallDelta` をそのまま消費する（フォールバック）。倍速で position が x 秒進んだなら費やした実時間は x / rate 秒であり、`wallDelta` を上限に置くことで前方シークでも過大請求しない。後方シークした tick は消費 0
  - バックグラウンドで tick が欠落しても、鳴っていた時間ぶんは positionDelta に現れるため正しく消費される。逆にポーズしていた時間は positionDelta が伸びないため消費されない
- Pro ユーザーは `AllowanceEnforcer.tick` の冒頭でガードされ、消費・停止予約のいずれも行わない

## Acceptance Criteria

- タイムゾーンを変更しても、24時間以内に二重リセットが起きない
- 端末の時計を過去に戻しても、残高・トライアル終了時刻が巻き戻らない
- 初回起動から 168 時間はトライアルとして扱われ、残高を消費しない
- 残高が尽きても、再生中の曲が終わるまでは倍速再生が継続する
- 曲が終わった時点で自動的に再生が停止し、`AllowanceSheetView` が表示される
